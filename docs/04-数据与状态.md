# 04 · 数据与状态

> 上层入口：`../AGENTS.md` ｜ 相关：`02-功能规格.md`

## 1. 存储位置

```
/data/data/com.zhuri.daybyday/files/zhuri_data.json      ← 主文件
/data/data/com.zhuri.daybyday/files/zhuri_data.bak.json   ← 损坏时的备份
```

不申请存储权限，不写外部存储，不上传。卸载即彻底删除。

## 2. 文件格式（v1）

```json
{
  "version": 1,
  "tasks": [
    {
      "id": "a1b2c3",
      "title": "读 20 页书",
      "note": "第 3 章，做笔记",
      "startDate": "2026-11-06",
      "repeat": "DAILY",
      "weekDays": [1, 3, 5],
      "monthDay": 1,
      "time": "08:00",
      "createdAt": 1762406400000
    }
  ],
  "done": ["a1b2c3|2026-11-06", "a1b2c3|2026-11-07"]
}
```

- `repeat`：`NONE | DAILY | WEEKLY | MONTHLY`，未知值按 `NONE` 处理（向前兼容）。
- `weekDays`：1=周一 … 7=周日，仅 WEEKLY 有意义，其它类型忽略。
- `time`：`HH:mm` 或 `null`。
- `done`：字符串数组，`<taskId>|<yyyy-MM-dd>`。用数组而非对象，方便增量去重。

## 3. 写入时机

| 触发 | 行为 |
|---|---|
| 新增 / 编辑 / 删除任务 | 立即写盘（`Dispatchers.IO`，事务式：写 tmp → rename） |
| 勾选 / 取消完成 | 立即写盘 |
| App 冷启动 | 只读，不写 |
| 后台被杀 | 无待写数据（因为每次变更都已落盘） |

**为什么每次变更都写**：数据量极小（几百条 < 30KB），一次写盘 < 3ms，换来「永不丢数据」。
写盘用单线程 `Dispatchers.IO.limitedParallelism(1)` 串行化，避免并发覆盖。

## 4. 原子写入实现要点

```kotlin
val tmp = File(dir, "zhuri_data.tmp")
tmp.writeText(json)
if (!tmp.renameTo(file)) { file.delete(); tmp.renameTo(file) }
```
断电 / 崩溃时最多丢最后一次操作，不会产生半个 JSON。

## 5. 状态流

```
TaskRepository
├── val tasks: StateFlow<List<Task>>        // 只读，UI collect
├── val done:  StateFlow<Set<String>>       // 只读
└── fun add / update / delete / toggle       // 唯一写入口
```

- 单例由 `ZhuriApp` 创建，`Root()` 通过 `LocalContext` 取 `application as ZhuriApp`。
- UI 全部用 `collectAsStateWithLifecycle()` 订阅（`lifecycle-runtime-compose`）。
- **派生数据不存**：某天的应做列表、完成度、streak 全部在 `remember(tasks, done, today)` 里现算。
  这样任何写操作都天然一致，不需要「同步两份状态」。

## 6. 版本升级策略

- `version` 字段用于判断是否需要迁移。
- 加字段：给默认值即可，读取时 `optString / optInt` 容错，**不升 version**。
- 改语义（如把 `done` 从数组换成对象）：升 version，在 `load()` 里做一次性迁移，迁移成功后立刻回写。
- 读失败（JSON 异常、字段类型错）：把原文件改名成 `.bak.json`，以空数据启动，绝不让 App 崩在启动页。

## 7. 为什么不用 Room

- 数据量：几百条任务、几年完成记录，全量加载 < 1MB，内存完全放得下。
- 查询：所有查询都是「某天的发生集合」，用 `filter { it.occursOn(d) }` 一次遍历，微秒级。
- 代价：Room 会引入 KSP（编译变慢、构建链条变长）和 schema 迁移负担。
- 结论：**JSON 文件 + 全量内存**在这个体量下更快、更简单、更不容易出错。数据量超过 5000 条再考虑迁移。
