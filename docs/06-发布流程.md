# 06 · 发布与更新日志流程

> 目标：每一版都能让用户看懂「改了什么、修了什么」，同时不制造一堆碎片文件。

## 1. 组织方式（结论）

**一个版本 = 一份发布说明**，放在 `docs/releases/v<版本>.md`。
不按「每个 bug 一个文件夹」拆分。原因：

- 用户关心的是「这一版值不值得更新」，版本才是发布单位；
- 一个 bug 从发现到上线可能跨多次提交，按 bug 建文件会变成无法检索的碎片；
- 同一天多个修复如果各发一版，版本号会膨胀，用户也不知道该装哪个。

因此：

| 情况 | 做法 |
|---|---|
| 普通功能 / 改进 | 进入下一个 minor 版本，例如 v3.1 |
| 普通 bug 修复 | 并入下一版，写在「修复」小节 |
| 紧急线上问题 | 发补丁版本，例如 v3.0.1，单独一份说明 |
| 预发布打磨 | 可写 v1.0 这类预发布说明，并注明并入哪个正式版 |

## 2. 目录结构

```
docs/
├── CHANGELOG.md              ← 完整技术流水账（按时间倒序）
└── releases/
    ├── README.md             ← 用户看的版本索引（脚本自动生成）
    ├── v3.0.md               ← 该版本具体新增 / 改进 / 修复
    ├── v2.1.md
    └── ...
```

`docs/releases/README.md` 只放索引表：版本、日期、类型、一句话摘要、链接。
具体内容全部在版本文件里，索引不重复正文。

## 3. 每次发版的固定步骤

1. **定版本号**：功能用 `x.y`，修复用 `x.y.z`；`versionCode` 必须 +1。
2. **写发布说明**（打包前）：
   ```bash
   python scripts/new_release.py 3.1 "分类支持拖动排序" \
     --type 体验改进 --summary "分类可以长按拖动排序，常用分类排前面"
   ```
   然后补全文件里的「新增 / 改进 / 修复」三节；没有内容的小节删掉。
3. **补 CHANGELOG**：在 `docs/CHANGELOG.md` 顶部加一条同版本记录（技术视角可以更细）。
4. **改版本号**：`app/build.gradle.kts` 的 `versionCode` / `versionName`。
5. **构建 Release**：`gradle assembleRelease`，产物复制为 `artifacts/逐日-v<版本>.apk`，删除上一版 APK。
6. **真机验收**：覆盖安装（不卸载）确认数据还在；跑一遍新增功能与关键回归。
7. **提交并双推**：
   ```bash
   git add -A && git commit -m "feat: v3.1 ..."
   git push origin main
   git push gitee main
   ```
8. 三端核对：本地 / GitHub / Gitee 的 commit 一致，README 下载链接指向新版本。

## 4. 写发布说明的规范

- 标题：`v<版本> · <一句话主题>`，主题不超过 20 字。
- 开头三行：发布日期、版本类型、一句话摘要（和索引一致）。
- 正文分三节，按需保留：
  - **新增**：用户能感知的新能力；
  - **改进**：原有功能变得更好用、更快、更清楚；
  - **修复**：具体描述「原来怎样 → 现在怎样」，不要只写「修复 bug」。
- 用用户语言，不写类名、文件名、commit hash。
- 涉及数据或安装方式变化，单独加「升级说明」。

## 5. 索引维护

不要手工排序。新增或修改版本文件后运行：

```bash
python scripts/new_release.py --index
```

脚本会读取每个文件顶部的 `version / date / type / summary`，按日期与版本号倒序重写索引。
因此**每个版本文件的 front matter 必须完整**，否则不会出现在索引里。

## 6. 可选：平台 Release

如果之后要在 GitHub / Gitee 建 Release，直接把对应 `docs/releases/v<版本>.md` 的正文粘过去即可，
标题用 `v<版本>`，附件用 `artifacts/逐日-v<版本>.apk`。仓库内文件与平台 Release 内容保持一致。
